### Tables

**`admins`**: `email citext primary key`, `created_at`.
RLS: no policies for anon or authenticated (nobody can read or write through the API). `is_admin()` is a `security definer` function that checks the signed-in user's email against this table.

**`profiles`** (one per founder)
- `user_id uuid pk references auth.users on delete cascade`
- Layer 0: `school school`, `student_status student_status`, `state text` (Q1), `city text`, `stage stage`, `sector sector`, `incorporated boolean`
- Layer 2: `incorporation_state text` (Q1), `founded_on date` (Q1), `university_ip boolean` (Q1), `team_size` (Q1), `paying_customers` (Q1), `monthly_revenue_range` (Q1), `funding_needed` (Q1), `funding_deadline date`, `equity_ok boolean`, `us_citizen_or_pr boolean`
- `milestones milestone[] not null default '{}'`
- `email_digest boolean default true`, `email_reminders boolean default true`, `email_checkins boolean default true`
- `calendar_token_hash text` (the raw token is shown once, only the hash is stored)
- `created_at`, `updated_at`
- Every Layer 0 and Layer 2 column is nullable. `null` means "not answered".

RLS: owner select, insert and update where `user_id = auth.uid()`. No delete through the API (Q14). **No admin policy**: admins never read profile rows. Metrics come only from aggregate functions.

**`profile_founder_groups`**: `user_id pk`, `groups founder_group[]`, `answered_at`. A missing row means not answered. An empty array means "answered, none apply". Kept apart from `profiles` so no admin, share or aggregate query can touch it by accident.
RLS: owner only. Nothing else reads it, and the aggregate functions never join it.

**`opportunities`**
- `id uuid pk`, `slug text unique`, `name`, `organizer`, `type opportunity_type`, `geography_level geography_level`, `regions text[]`, `description`
- `amount_min int`, `amount_max int`, `amount_notes` (all nullable)
- `equity_required boolean not null default false`, `equity_notes`
- `deadline_type deadline_type`, `opens_at date`, `deadline_at date`, `decision_at date`, `cycle_notes`
- `application_url`, `source_url`
- `eligibility_rules jsonb not null default '[]'`, `application_questions jsonb not null default '[]'`, `past_winners jsonb not null default '[]'`
- `target_groups founder_group[] not null default '{}'`, `materials_required material_key[] not null default '{}'`
- `past_results_text`, `past_results_count int`, `past_results_year int`, `past_results_source_url`
- `verification_status verification_status not null default 'unverified'`, `last_verified_at timestamptz`, `verified_by citext`
- `archived boolean not null default false`, `created_at`, `updated_at`

RLS:
- anon and authenticated: select where `verification_status <> 'unverified' and not archived` (Q4)
- organizer: select and update where an approved claim links `auth.uid()` to this row
- admin: all
- A trigger blocks non-admins from changing `slug`, `verification_status`, `last_verified_at`, `verified_by` and `archived`.

**`opportunity_research_notes`**: `opportunity_id pk`, `notes`. Admin only. Kept in its own table because Postgres RLS works on rows, not columns, and `research_notes` is admin only.

**`opportunity_claims`**: `id`, `opportunity_id`, `user_id` (claimant must be signed in, Q12), `organization`, `role_title`, `message`, `status review_status`, `reviewed_by`, `reviewed_at`, `created_at`.
RLS: claimant reads their own claims. Insert only through the `claim-listing` function (rate limited). Admin all.

**`submissions`**: `id`, `submitter_email`, `payload jsonb` (Q13), `status review_status`, `reviewed_by`, `reviewed_at`, `created_at`. Insert only through `submit-opportunity` (Turnstile and rate limit). Admin read and update only.

**`materials`**: `user_id`, `material_key`, `kind` (file or link), `storage_path`, `url`, `updated_at`. Primary key `(user_id, material_key)`. Owner only.
**Storage bucket `materials`**: private. Paths are `{user_id}/{material_key}/{filename}`. Storage policies allow owner read and write on their own folder only. Downloads use signed URLs with a 60 second expiry.

**`answers`**: `user_id`, `answer_key`, `length answer_length`, `body text`, `updated_at`. Primary key `(user_id, answer_key, length)`. Owner only.

**`drafts`**: `user_id`, `opportunity_id`, `question_index int`, `body`, `updated_at`. Owner only. Edited drafts are saved, so work is not lost.

**`applications`**: `id`, `user_id`, `opportunity_id` (unique per user), `status application_status`, `stage_at_application stage`, `sector_at_application sector` (snapshotted when status first becomes `applied`), `amount_won int`, `reported_at`, `created_at`, `updated_at`. Owner only. No admin row access.

**`plan_snapshots`**: `user_id pk`, `statuses jsonb` (slug to status), `computed_at`. Owner only. Used for "Newly unlocked" and for the digest's "new matches".

**`share_links`**: `id`, `user_id`, `token_hash`, `mode` (password or invite), `password_hash`, `expires_at`, `revoked_at`, `open_count`, `created_at`. Owner can select and revoke. Created only through `share-create`, so passwords are hashed server side.
**`share_invites`**: `share_id`, `email citext`. Owner only.

**`checkin_tokens`**: `jti uuid pk`, `application_id`, `action`, `expires_at`, `used_at`. No API access, Edge Functions only. A signed link is valid only if the HMAC verifies, it hasn't expired, and `used_at` is null. It is marked used in the same transaction as the update.

**`email_log`**: `user_id`, `kind email_kind`, `ref text`, `sent_at`. Stops duplicate reminders and check-ins. Edge Functions only.

**`rate_limits`**: `bucket`, `key_hash`, `window_start`, `count`. Edge Functions only. IPs are stored hashed.

**`events`**: `id bigserial`, `name event_name`, `user_id uuid null`, `anon_id text null`, `school school null`, `sector sector null`, `created_at`. Insert allowed for anon and authenticated with check `user_id is null or user_id = auth.uid()`. Select is admin only. No founder groups and no free-text properties.

### Aggregate functions (`security definer`, admin-checked or threshold-checked)
- `founders_like_you(opportunity_id, stage, sector)` returns `{reported, won}` only when `reported >= 10`, otherwise null. The threshold is enforced in the database too, so small counts never leave it.
- `metrics_summary(from, to)`, `metrics_by(dimension)`: admin only, counts from `events` and `applications`. Never returns row-level data.

## 5. Questions that need your decision

Each one has my suggested default. You can reply "defaults OK" or answer by number.

**Field definitions**
- **Q1. Fields with no defined type or values.** Suggested:
  - `state` and `incorporation_state`: the two-letter codes for the 50 states, DC and PR, plus `outside_us`.
  - `city`: free text.
  - `founded_on`: a month and year.
  - `university_ip`: yes, no or not sure.
  - `team_size`: buckets 1, 2 to 3, 4 to 10, 11 or more.
  - `paying_customers`: buckets 0, 1 to 10, 11 to 100, more than 100.
  - `monthly_revenue_range`: none, under $1k, $1k to $10k, $10k to $50k, over $50k.
  - `funding_needed`: under $10k, $10k to $50k, $50k to $250k, over $250k.
  - `funding_deadline`: a date.
- **Q2. SBIR and US ownership.** SBIR eligibility depends on majority US ownership of the company, but `us_citizen_or_pr` asks about one person. Options: (a) keep the field and word it as "Are you a US citizen or permanent resident?", and let SBIR rules use it as an approximation, (b) add a Layer 2 field `majority_us_owned`. Suggested: (b), with `us_citizen_or_pr` kept for fellowships that require it.
- **Q3. Milestones that overlap fields.** Suggested: marking `incorporated` sets the `incorporated` field. Marking `prototype_built`, `first_pilot` or `first_revenue` raises `stage` to prototype, pilot_users or revenue if it's lower, and never lowers it. `graduated` does not change `student_status` by itself, but asks the founder to update it.

**Matching**
- **Q4. Does `organizer_verified` count as verified** for the plan, totals, advisor and map? Suggested: yes. And do organizer edits go live at once, or back to your queue? Suggested: they go live, the listing is flagged in your verification queue, and `last_verified_at` is reset to the edit date.
- **Q5. Status when an eligibility rule is unknown and a readiness rule fails.** The spec's definitions don't cover this case. Suggested: Not ready yet, showing the gap and the unanswered question.
- **Q6. Dates.**
  - Rolling with no deadline: Apply now if `opens_at` is past or empty.
  - Recurring with a passed deadline: the spec says to include "the next cycle", but there is no field for the next cycle's dates. Suggested: shift the last cycle forward by whole years, labeled "Expected, based on last cycle. Confirm with the organizer." The alternative is to leave it out until you update the dates.
  - Fixed and passed: not in the plan.
  - Eligible but opening more than 9 months out: a quiet line ("2 more open later than 9 months from now").
  - All dates in Eastern time. "9 months" means calendar months.
- **Q7. Next-unlock advisor.** What does it simulate for unanswered Layer 2 fields, and how should it phrase them? Suggested: milestones are phrased as actions ("Getting your first paying customer would..."). Unanswered fields are phrased as "Answering incorporation state could show you up to N more programs", and it tries only values that appear in some rule. `us_citizen_or_pr` and founder groups are never suggested. The count and amount both use verified, non-equity programs only.
- **Q8. Targeted programs once founder groups are answered.** Suggested: target groups mean "any of". If the founder matches, the program goes into the normal plan. If they answered and don't match, it counts as not eligible. "Prefer not to say" is treated as not answered, so the separate section keeps showing.
- **Q9. Total wording.** "up to $X across N opportunities": should N count only the programs in the sum? Suggested: yes. Undisclosed-amount and equity programs are described on their own lines.
- **Q10. "Founders like you" counts which outcomes?** Suggested: only `won` and `not_selected` count as reported outcomes. Shown as "3 of 10 won".

**Data, privacy and sharing**
- **Q11. Testing with unverified seeds.** The 5 EXAMPLE rows import as unverified, so they won't appear in any founder view until you verify them in admin. Suggested: test fixtures (not seed data) verify them inside automated tests only, and you verify them yourself in the app when you want to look around.
